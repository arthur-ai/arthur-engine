## Progress
- Implemented BE fix for "Relative time filters return no results despite matching data".
- Added `TaskSortField` enum (`created` / `updated`) as the single source of truth for which timestamp column drives filtering + ordering.
- `TaskRepository.query_tasks` now accepts `sort_field`, `start_time`, `end_time`. It resolves the timestamp column from `sort_field` and applies BOTH range bounds and the ORDER BY to that resolved column. Default (unset) mode = `created_at` (unchanged behavior).
- Wired `search_tasks` route (`POST /api/v2/tasks/search`) to accept `sort_field`, `start_time`, `end_time` as query params (SearchTasksRequest body is external/pinned in arthur_common, so added them as route Query params instead).
- Extended test client `search_tasks` with the new params.
- Added regression tests (repository + endpoint level).
- Updated `staging.openapi.json` + `src/api_changelog.md` (oasdiff binary unavailable, did the equivalent manually).

## Decisions Made
- The actual "All tasks" filtering was done client-side in `AllTasks.tsx` over paginated pages ordered by `created_at`; a month-old-but-recently-updated task sat deep in the created_at ordering and was never loaded → "no results". Fixing the BE so ordering + time filter follow the selected mode is the correct BE-side fix.
- Used route-level Query params (not the request body) because `SearchTasksRequest` lives in the pinned external `arthur_common` package (v2.4.67) and can't be edited here.
- Range bounds: `sort_column >= start_time` and `sort_column <= end_time`.
